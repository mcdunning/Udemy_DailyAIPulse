**Current state and what was done:** DailyAIPulse is a native Android MVP (Kotlin, Jetpack Compose, MVVM+Repository, Hilt DI, no domain layer). All three planned features — Article List, Source List, AI Summarization — are complete and merged (PRs #1–#11); this project's original feature roadmap is done. Since then, three post-MVP hardening PRs landed: **PR #13** locked `MainActivity` to `android:screenOrientation="portrait"` (the UI isn't designed for landscape). **PR #14** added `./gradlew jacocoFullTestReport` (merges unit + instrumented coverage into one report with an informational PASS/FAIL note) and a real enforcement gate — `./gradlew assembleRelease`/`bundleRelease` now fail via `jacocoCoverageVerification` if combined instruction coverage is under 80%. **PR #15** (this pass) discovered that PR #14's gate would have failed release builds outright — actual coverage was 58.2%, not close to 80% — and fixed that for real, taking coverage to 93.0% and confirming `./gradlew assembleRelease` now succeeds end-to-end.

**Files updated/created, mistakes to avoid, and lessons learned:** The 58.2% baseline was not a real testing gap — most hand-written logic was already 90–100% covered. Two structural issues caused the low number, both fixed in PR #15: (1) Compose `@Preview` functions can never execute under any unit or instrumented test (they're Android-Studio-tooling-only), yet JaCoco counted every one as missed instructions — fixed by adding `com.dailyaipulse.core.GeneratedPreview` (an annotation whose simple name contains "Generated") and applying it to all 16 `@Preview` functions across `ArticleListContent.kt`/`ArticleListItem.kt`/`SourceListContent.kt`/`SourceListItem.kt`, which opts them into JaCoco's built-in `AnnotationGeneratedFilter` (confirmed working in this exact AGP 9.3.2/Kotlin-built-in/JaCoco 0.8.14 toolchain via a disposable spike before committing to the approach — **any new `@Preview` function must also carry `@GeneratedPreview`, or coverage will silently regress**; see the architecture doc's 2026-09-20 addition). (2) Everything requiring `hiltViewModel()` — `ArticleListScreen`, `SourceListScreen`, `AppNavigation`, `MainActivity` — had zero instrumented-test coverage because this project had no Hilt test infrastructure; fixed by adding `app/src/androidTest/java/com/dailyaipulse/HiltTestRunner.kt` (wired as `testInstrumentationRunner`) plus `hilt-android-testing`/`kspAndroidTest(hilt-android-compiler)`, and a new `MainActivityTest` that launches the real `MainActivity` via `createAndroidComposeRule` + `HiltAndroidRule` and covers all four classes in one Activity launch. That test uses the **real, unmocked Hilt graph** (Repository classes are concrete, not interfaces, so there are no test-double bindings) — ViewModels fire real NewsAPI/Gemini network calls on launch, so assertions only check each screen's static `TopAppBar` title (new `testTag("screenTitle")`, needed because the bottom-nav label and the title share the same text and would otherwise be ambiguous to `onNodeWithText`), never network-loaded content, to avoid flakiness. Also added: a `ThemeTest.kt` exercising `DailyAIPulseTheme`'s dynamic/dark/light branches directly; `NewsApiKeyInterceptorTest`/`GeminiApiKeyInterceptorTest` unit tests; existing `ArticleListContentTest`/`SourceListContentTest` now wrap `setContent` in `DailyAIPulseTheme { }` (matching production rendering) instead of rendering bare, which incidentally covers `ui.theme`; and a `jacocoExcludes` glob fix (`**/*_Provide*Factory*.*`) for Hilt-generated `NetworkModule_Provide*Factory` classes that the existing `**/*_Factory.*` pattern didn't match (no underscore before "Factory").

**Problems, requirements, and open items:** `./gradlew testDebugUnitTest` passes (30/30 tests) and `./gradlew connectedDebugAndroidTest` passes (23/23 tests) on a physical device; `./gradlew jacocoFullTestReport` reports 93.0% (PASS against 80%) and `./gradlew assembleRelease` succeeds, confirming the enforced gate is genuinely satisfied, not just the informational one. One known non-blocking report-generation quirk: `jacocoFullTestReport` logs `Classes in bundle 'app' do not match with execution data ... Execution data for class com/dailyaipulse/MainActivity does not match` and shows the `com.dailyaipulse` package (MainActivity + DailyAiPulseApplication, ~34 instructions) as 0%/unattributed even after a clean rebuild, despite `MainActivityTest` genuinely passing on-device — cosmetic (doesn't affect the 93.0% total or the enforced gate), not investigated further since it isn't blocking. `MainActivityTest` requires the same valid `NEWS_API_KEY`/`GEMINI_API_KEY` setup as manual testing and will make real network calls in the background during `connectedDebugAndroidTest`. The four non-blocking gaps flagged after AI Summarization (PR #11) — unconditional API-key logging in `HttpLoggingInterceptor`, an imprecise Gemini "no usable content" error shape, thin `SummaryRepositoryTest` edge-case coverage, and the terminal per-tab `Error` state — remain open, untouched by this pass. Not done, and out of scope for this pass by explicit decision: Play Store distribution readiness (signing config, R8/minification — `release` still has `optimization { enable = false }`, store listing assets); this was a codebase-cleanup-and-coverage milestone, not a distribution pass.
